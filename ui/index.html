An engineering study in constrained agent autonomy

We gave an AI agent 50 failed payments. Then we tried to find out whether it deserved the right to recover them.

We didn't set out to prove that agents are better. We set out to measure what happens when one is allowed to make financial recovery decisions — and where deterministic controls still matter. Every proposal, policy decision, execution, failure and refused action is published in the repository.

01 — How it works

Detect the risk, choose the intervention, execute inside a boundary.

Seventy-five synthetic cases across three kinds of revenue at risk — failed payments, abandoned checkouts and overdue receivables. The agent reads a case and proposes one action; a deterministic policy engine authorises or refuses it; only what survives executes. Every step is written to an append-only ledger.

The agent never touches money. Reaching the payment provider requires an AuthorizedAction, and that object can only be constructed inside the policy module — so a route from proposal to execution that skips policy raises an exception rather than moving funds.

02 — What the agent does that a rule set cannot

It writes to the customer.

A rule set chooses an action from a closed menu. It cannot compose a sentence, so every message it sends is one template with the numbers swapped. The agent reasons about the specific failure and the specific customer, and writes the message itself — then that message goes through a second deterministic boundary before it can be sent.

These are real drafts, committed to data/messages/composed.json. One of them is refused: asked to write about an abandoned checkout, where nothing was ever authorised, the agent described a card on file that does not exist. The content policy blocks it. The prompt is guidance; the boundary is enforcement.

06 — Every decision, on the record

Decision replay

Reconstruct the agent's observable decision path from the ledger — what it saw, what it proposed, what policy allowed, what happened. Claims it restated about a case are checked against the state it was actually shown, so a contradicted premise sits next to the decision it produced. Start with the cases it handled correctly; the filters open up the rest.

07 — The counterpoint

The agent was allowed to be wrong. It was never allowed to move money however it wanted.

This is the half of the result that did work. We did not make the agent trustworthy — we declined to trust it, and measured what happened when it tried anyway.

08 — Open the black box

Nothing here is a screenshot pretending to be evidence.

Every figure on this page is derived from files committed to the repository — the dataset the runs consumed, the ledger they wrote, and the metrics computed from it. The database is not the source of truth; the files are, because a schema drop already destroyed one set of results during this project.

Reproduce
cp .env.example .env          # add your own OpenAI-compatible endpoint
createdb agent_finance

python -m afin.experiment.run --arm baseline          # deterministic, no model, no cost
python -m afin.experiment.run --arm agent --profile primary

python analysis/divergence.py        # baseline vs agent, per payment
python analysis/feedback.py          # failure → next-decision transitions
python analysis/build_console_data.py && python analysis/build_ui.py

Synthetic data only. Every payment and customer in this repository is generated from a seeded PRNG. No real customer, payment or communication data exists anywhere in the project, and no real financial transaction was ever made — the payment provider is a simulator that opens no sockets.

We didn't build a trustworthy agent. We built a system that can measure whether one is becoming trustworthy.
