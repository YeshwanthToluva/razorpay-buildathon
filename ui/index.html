We gave an AI agent 50 failed payments. Then we tried to find out whether it deserved the right to recover them.

A reproducible experiment in agentic financial operations. Every proposal, policy decision, execution, failure and refused action in this study is published in the repository.

Exploratory. n = 1 per agent arm; run-to-run variance not estimated. Observed spread across repeats of the same configuration is several percentage points.

01 — The question

Can an agent outperform a deterministic recovery policy?

Fifty synthetic failed payments, ₹3,59,088 at risk. Both contestants see the same dataset, the same seed and the same policy engine. The agent proposes an action; a deterministic policy authorizes or refuses it; a seeded simulator executes what survives. Every step is written to an append-only ledger.

The agent never touches money. Reaching the payment provider requires an AuthorizedAction, and that object can only be constructed inside the policy module — so a route from proposal to execution that skips policy raises an exception rather than moving funds.

02 — The baseline

First, the boring answer.

A rule set with no model in it. Retry transient failures, defer soft declines, send a payment link when the instrument is dead, stop when the budget is spent.

So what happens when we let the agent decide?

04 — What we tried

Twice we improved what the agent knew.

Each experiment changed exactly one variable, holding model, dataset, seed, policy, autonomy and simulator constant.

So the problem was not what the agent knew.
It was what the agent chose to do.

05 — Where it went wrong

The interesting failures were not crashes.

They were decisions that passed every check and were still economically wrong. Each payment is classified by comparing the agent against the baseline on the identical case. "Correct action" is not a judgement call — it is the highest-probability action for that failure category under the simulator's own published physics.

06 — Show me the failure

07 — The counterpoint

The agent was allowed to be wrong. It was never allowed to move money however it wanted.

This is the half of the result that did work. We did not make the agent trustworthy — we declined to trust it, and measured what happened when it tried anyway.

08 — Open the black box

Nothing here is a screenshot pretending to be evidence.

Every figure on this page is derived from files committed to the repository — the dataset the runs consumed, the ledger they wrote, and the metrics computed from it. The database is not the source of truth; the files are, because a schema drop already destroyed one set of results during this project.

Reproduce
cp .env.example .env          # add your own OpenAI-compatible endpoint
createdb agent_finance

python -m afin.experiment.run --arm baseline          # deterministic, no model, no cost
python -m afin.experiment.run --arm agent --profile primary

python analysis/divergence.py        # baseline vs agent, per payment
python analysis/feedback.py          # failure → next-decision transitions
python analysis/build_console_data.py && python analysis/build_ui.py

Synthetic data only. Every payment and customer in this repository is generated from a seeded PRNG. No real customer, payment or communication data exists anywhere in the project, and no real financial transaction was ever made — the payment provider is a simulator that opens no sockets.

We didn't build a trustworthy agent. We built a system that can measure whether one is becoming trustworthy.
