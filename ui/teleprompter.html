00 · Open25s · camera

[Site on screen, nothing running. Say it plainly. Do not perform it.]

Three things quietly lose revenue for anyone taking payments online. A payment fails. A customer leaves checkout. An invoice goes past due.

In all three the money already exists. It just does not arrive.

We built an agent that goes and gets it. The interesting part is not that it works. It is what we had to build so it is safe to run.

01 · What it does30s

It handles those three kinds of revenue at risk.

It can take six actions. Retry the payment. Schedule a retry. Send a payment link. Send a reminder. Ask a human. Stop.

That list is closed. If the model names anything outside it, the request is rejected before anything else is even looked at.

02 · The boundary55s · the core

[Switch to agent.html — the map. Let it sit on screen while you talk.]

The model proposes. It never executes.

Between the proposal and the money there is a policy engine. Fifteen rules, fixed order, first refusal wins, and the list ends in default-deny. Pure code — no model, no network, no database.

This is not a convention we agreed to follow. The provider that moves money only accepts a type called AuthorizedAction. That type can only be constructed inside the policy module. Build one anywhere else and you get PolicyBypassError.

So you cannot skip the check by accident. There is no route to the money that goes around it.

This map is generated from the code, not drawn by hand. Every line from an action to a rule was measured by running that action against every case in the dataset.

04 · The tools30s · Composio

The email is real. It goes out through Composio's Gmail MCP tool on a connected account.

A Gmail toolkit can read mail, list contacts, manage drafts. This agent has one action — GMAIL_SEND_EMAIL. Anything else raises ToolScopeError.

And who it may email is not decided by the mail tool. It is decided by the policy engine, before the tool is reached at all.

05 · Does the boundary hold55s

[Safety section. Then click one blocked attempt.]

Across our runs the agent proposed 137 actions the policy engine did not authorise.

113 refused outright. 24 were high value and routed to a human — and there is no human at this autonomy level, so those did not run either.

Actions that reached the provider without approval: zero. In every run.

These are not screenshots. Click any refusal and it re-runs that request against the live engine — the verdict, the rule that decided, and every rule it checked on the way.

06 · Why a model at all60s

If the rules are that strict, why use a model.

Same failed payment, two messages.

on screen · inv_0042 · ₹1,776 · 9 payments, 5 successful

The rule set

We were unable to collect Rs 1,776.00 for invoice inv_0042, because your bank declined the payment. You can settle it using the link below.

The agent

We couldn't collect Rs 1,776.00 for invoice inv_0042 because the payment attempt was declined.

This was the first attempt, and a second try often goes through. If your card has expired or been replaced, please use a different payment method.

If you have any questions, just reply here and we'll help.

The rule set says the bank declined it. Every customer gets that same sentence.

The agent says this was the first attempt and a second usually goes through — because this customer has paid nine times and five went through clean. Then it offers a way out, and invites a reply.

[Scroll to the third message — the refused one.]

And here is the same agent on an abandoned checkout, where nothing was ever authorised and there is no card.

content policy · REFUSED · CONTRADICTS_THE_CASE
The card on file appears to be unavailable for this charge.
nothing was ever authorised on this case, so no card exists and no charge was attempted

There is no card. The model invented one. That message was never sent — the template went instead, and the refusal is in the record.

That is the trade. The model writes better. The boundary is what makes it safe to let it.

07 · What we actually found40s

[The docs folder, or the experiments list.]

We ran 21 recorded runs and wrote four experiment records. Two of them falsified what we expected.

We expected the agent to recover more than a fixed rule set. It recovered less. We published that.

We thought it needed better context. Then we thought it needed to know its retries had failed. Both improved what the agent knew. Neither changed what it recovered — the second one identical to the rupee.

So the remaining gap is not an information problem. That is in the repo, negative results kept in.

Q&A · backupnot part of the take

All data is synthetic. No real customer or payment data, and no real money moves — the payment rail is a simulator.

The email allowlist holds one address and is enforced in the policy engine, not the mail tool. An empty allowlist denies everyone, so a misconfigured deploy sends nothing.

Simulator outcomes are a keyed hash of seed, payment, action and attempt, so a result never depends on what order cases ran in.

The policy fingerprint covers the thresholds and the rule list, so adding a rule changes it. Every run records the fingerprint it ran under.

Autonomy Level 2 — model proposes, deterministic policy disposes, no human in the loop. Escalation is therefore terminal, which is why over-escalation cost the agent revenue; we measured it at 94.6% of the gap.
