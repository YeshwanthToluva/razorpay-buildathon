The deterministic boundary

Every rule the agent has to get past.

The agent may propose anything at all. This is the code that decides whether it happens. It is pure and deterministic — no model, no network, no database — and it is the only place an AuthorizedAction can be created, which is the object a payment provider refuses to act without.

The rules, in evaluation order

These are rules, not actions. A rule is a check the engine runs; an action is what the agent asks to do. The six actions live further down. They run top to bottom and the first refusal wins, so a payment that is both disputed and past its recovery window reports the dispute — the more serious cause is the one written to the ledger. The table ends in a default denial: anything not explicitly permitted is refused, so adding an action without deciding its policy makes it unusable rather than allowed.

The limits it enforces

Thresholds are configuration, not law. Changing one changes the policy fingerprint, which is recorded on every run — so two experiments run under different limits can never be silently compared.

The actions it will consider

A closed set. Anything outside it is refused as an unsupported action, which is how an agent is prevented from inventing financial operations.
